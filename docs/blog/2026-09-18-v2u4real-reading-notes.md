# V2U4Real 阅读笔记：车和无人机怎么一起看清环境

这次读 V2U4Real，我是从几个很基础的问题开始的：3D perception 和自瞄里的解算有什么关系？点云怎么送进网络？无人机换个角度看，就能帮车看得更清楚吗？

读到后面，我又开始想无人机的续航，以及两架无人机能不能轮流工作。这篇笔记把这些问题串起来，也留住我暂时还没弄清楚的地方。主要整理概念和论文实验，没有做模型复现。

## 单车看不到的地方，空中视角能补多少

V2U4Real 研究的是 Vehicle-to-UAV（V2U）协同感知：地面车辆和无人机共享信息，一起做三维目标检测和跟踪。

开到路口时，前面一辆大车可能挡住旁边的行人；建筑后面有车，但车载传感器还没看到；目标离得远，LiDAR 打到它身上的点又很少。给车多装一个传感器，仍然可能受同一个地面视角限制。无人机的位置和高度不同，有机会看到另一部分环境。

我先用这个简图记住场景：

```text
                  UAV
                   ↓ 空中观测
              被遮挡的目标
                   │
Vehicle →       大车 / 建筑
  地面视线在这里被挡住
```

这里的“有机会”很重要。无人机也有视野、量程和遮挡限制，高视角能提供互补信息，具体收益仍然取决于它飞在哪里、传感器朝哪里。

论文的主要贡献是建立真实世界的 V2U 数据集和 benchmark，让单体检测、协同检测、协同跟踪有共同的测试环境。它采集了 LiDAR 和 RGB 图像，不过本文的主要协同实验围绕 LiDAR 展开。数据集包含多模态数据，和实验已经充分解决多模态融合，是两件事。见[论文的任务定义和实验设置](https://arxiv.org/html/2603.25275v1#S4)。

## 3D perception 和我接触过的解算

普通二维检测告诉我“图像里哪里有目标”。三维感知还要知道它在真实空间中的位置、尺寸和朝向。常见的简化三维框可以写成：

```text
box = (x, y, z, l, w, h, θ)
       位置     尺寸      朝向
```

这是便于理解的七参数形式。V2U4Real 的标注还记录了 roll、pitch、yaw，不能把无人机相关的旋转都压成一个平面角度。

我最开始把 3D perception 理解成一个具体算法，后来才分清：它是一个问题领域，点云处理、三维检测、深度估计、定位、跟踪和融合都可能参与其中。PnP 则是其中可以用到的几何方法。

拿 RM 自瞄来对照，就比较好理解了：

```text
装甲板角点 + 已知尺寸 + 相机参数
                  ↓ PnP
           相机坐标系中的目标位姿
                  ↓ 坐标变换
          云台 / 车体 / 世界坐标系
```

这让我对论文里的坐标变换没那么陌生。场景更复杂，但仍然需要明确“这个位置是谁的坐标系里的位置”。PnP 的输入和输出也可以对照 [OpenCV 文档](https://docs.opencv.org/4.13.0/d5/d1f/calib3d_solvePnP.html)检查。

## LiDAR 先给点，PointPillars 再把点整理成特征

LiDAR 通过激光测距形成点云。一帧数据可以理解成很多这样的点：

```text
pᵢ = (xᵢ, yᵢ, zᵢ, intensityᵢ)
```

它们表示传感器采到的表面位置和反射强度，本身没有“这是汽车”的语义标签。点云通常稀疏、不规则，每帧点数也可能不同。直接照搬处理 RGB 图像的规则二维卷积，并不方便。

PointPillars 的做法是先把 XY 平面划成网格，每个格子沿 Z 方向形成一根柱子，也就是 pillar。在设置好的高度范围内，Z 不再细分成多层。Voxel 则通常沿 XYZ 三个方向切格子。

每根柱子里的点经过类似 PointNet 的编码，汇总成固定长度的特征，再按原来的 XY 位置放回网格，得到形状为 `H × W × C` 的 pseudo-image。后面的网络就能用 2D CNN 提取特征，最后预测三维框。见[PointPillars 原论文](https://openaccess.thecvf.com/content_CVPR_2019/papers/Lang_PointPillars_Fast_Encoders_for_Object_Detection_From_Point_Clouds_CVPR_2019_paper.pdf)。

```text
点云 → 按 XY 分柱 → 柱内点编码 → 特征放回网格 → 2D CNN → 3D box
```

我之前记成“统一到二维坐标系方便计算”，这句话漏了一点：**空间索引变成二维网格，高度等信息仍然可以保留在特征通道里。** 它没有简单把所有点的 Z 坐标扔掉。

PointPillars 的设计比较重视速度，适合拿来理解实时检测的基础流程。不过实际系统的延迟还包含传感器采集、通信、对齐和后处理，不能只看网络推理速度。

## BEV 方便在哪里，两个 Agent 又怎么对齐

BEV 是 Bird's-Eye View，鸟瞰表示。对地面机器人来说，“前方 12 m、左侧 2 m”比“像素位置是 (523, 281)”更方便接入导航和避障。BEV 网格还可以存特征、高度、速度或置信度。

PointPillars 输出的二维空间网格天然适合这种表示。Camera、LiDAR、Radar 也可以通过各自的几何和编码方法构建 BEV，但映射过程有自己的误差，不是换个名字就统一好了。

车辆和无人机各自得到一份 BEV 特征，也不能直接相加。先看点的三维刚体变换：

```text
p_vehicle = R_uav→vehicle · p_uav + t_uav→vehicle

用齐次坐标写：p̃_vehicle = T_uav→vehicle · p̃_uav
```

`R` 是旋转，`t` 是平移，`T` 是 4×4 变换矩阵。选定车辆作为 ego 后，需要把无人机的信息表达在车辆参考坐标系中，再进行融合。

BEV 是表示方式，不自带“已经对齐”的保证。无人机会有完整的 6DoF 运动：`x、y、z、roll、pitch、yaw`。原始点云可以先做三维变换再编码；若在特征层对齐，也要考虑特征如何生成、投影和重采样。只用平面平移和 yaw 旋转，可能不足以处理较大的 roll、pitch 变化。

## Early、Intermediate、Late Fusion：到底传哪一层

这几个名字我容易混，按“传什么”来记比较稳。

| 方式 | 共享的内容 | 大致流程 | 需要权衡的地方 |
| --- | --- | --- | --- |
| Early Fusion | 原始数据，例如点云 | 对齐点云 → 合并 → 检测 | 保留的原始观测较多，传输量通常较大，错位和过时数据会进入检测网络 |
| Intermediate Fusion | 中间特征 | 各自编码 → 对齐并融合特征 → 检测 | 能按任务选择和压缩信息，通信量取决于特征尺寸、压缩与稀疏程度 |
| Late Fusion | 检测框、类别、置信度等结果 | 各自检测 → 对齐结果 → 合并去重 | 传输量通常较小，但没有共享那些尚未形成检测框的线索 |

Late Fusion 中，如果一方漏检、另一方检出了，融合结果仍然能补回来；两边都没输出框时，结果层就缺少原始点云或中间特征可继续利用。之前我把它记成“漏检后救不回来”，说得太绝对了。

这里的 trade-off 就是权衡、取舍。感知效果、通信量、实时性和鲁棒性会相互影响。Intermediate Fusion 提供了较灵活的设计空间，但它的传输量和效果都要看具体实现，不能只凭名字排序。

## Where2comm 选信息，CoAlign 处理空间错位

Where2comm 让我注意到一个问题：特征也可能很大，有些格子是背景，有些包含目标，整张图全部发送未必划算。

它用 spatial confidence map（空间置信度图）描述不同区域的感知信息，选择稀疏但对任务有用的区域进行通信。目标附近的高置信度信息可能帮助另一方补回漏检；多轮通信还可以结合接收方的请求。见[Where2comm 原论文](https://papers.nips.cc/paper_files/paper/2022/file/1f5c5cd01b864d53cc5fa0a3472e152e-Paper-Conference.pdf)。

我会用“优先传对另一方有帮助的区域”记它的动机，但不能直接把置信度图等同于一张准确标好的盲区地图。

CoAlign 关注的是 pose error。Pose 是位姿，包括位置和姿态。定位估计存在误差，就会把无人机的信息变换到错误的位置。例如下面只是一个平面化的示意：

```text
真实位姿：(10.0 m, 5.0 m, 30°)
估计位姿：(10.6 m, 4.7 m, 33°)

车辆观测：     [car]
无人机转换后：    [car]
```

同一个目标出现两份错开的特征，融合模块很难正确利用它们。CoAlign 利用 Agent 和目标之间的位姿图约束提高相对位姿的一致性，再进行多尺度特征融合。见[CoAlign 原论文](https://arxiv.org/abs/2211.07214)。

Where2comm 和 CoAlign 是 V2U4Real 测试的不同基线，分别帮助我理解通信选择和空间对齐。论文没有把它们机械串成一条“Where2comm → CoAlign”的固定流程；真要结合，需要重新设计接口和验证。

## AP@0.5，以及我现在怎么读结果表

IoU 是预测框和真实框的交并比。在这里的检测实验中，使用的是 **3D IoU**，对应体积的交并比：

```text
IoU = Volume(B_pred ∩ B_gt) / Volume(B_pred ∪ B_gt)

Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
```

固定类别、IoU 阈值和匹配规则后，把预测按置信度排序，得到 Precision–Recall 曲线，再按评估实现计算 AP。重复预测不能都算同一个目标的正确检测。

所以 `AP@0.5` 中的 `0.5` 是判断匹配时使用的 IoU 阈值，不是“准确率为 50%”。也不能因为输入使用了 BEV 特征，就把这里的 3D AP 当成 BEV AP。

我从[论文表 3](https://arxiv.org/html/2603.25275v1#S4.T3)摘了几项方便对照。它们是主实验 OS-128、验证集、Vehicle 类别（Car + Truck）的整体 **3D AP@0.5**，表中按百分数列出：

| 方法 | Sync | Async |
| --- | ---: | ---: |
| Vehicle only / No Fusion | 27.53 | 27.53 |
| Early Fusion | 51.31 | 30.94 |
| Where2comm | 53.85 | 48.99 |
| CoAlign | 56.67 | 50.81 |

这组数据里，CoAlign 的同步结果高于 Early Fusion，异步时也更稳。原始观测更多，还要看网络怎样处理这些观测。表格本身不能证明差距全都来自位姿校正，严格归因还需要消融实验。

读表时我也要检查评估范围、类别、标注集合和数据划分。尤其不能拿单体检测任务的 AP，直接和协同任务里的 No Fusion 比；它们使用的 ground truth 和评估设定有区别。

## 远距离和异步：信息够不够，信息新不新

远处目标难检测，一方面是点少。LiDAR 的角度采样下，相邻光束在远处的间距更大；目标表面、入射角和遮挡也影响回波。另一方面，地面视线可能被前方物体挡住。

```text
近处目标：••••••••••
远处目标：•      •
```

无人机提供另一组位置和视角的观测，有可能增加目标可见表面的点数。论文表 3 的同步 50–100 m 区间中，车辆单独感知的 AP@0.5 是 15.54，CoAlign 协同是 30.20。这是特定数据和模型下的结果，我更想记住它为什么能补到信息。见[远距离结果](https://arxiv.org/html/2603.25275v1#S4.T3)。

同步解决的是时间问题。两个传感器有时间差，数据传输也要时间。假设目标沿一个方向以 `10 m/s` 匀速运动，观测晚到 `0.5 s`，仅目标运动就会造成：

```text
Δx ≈ v · Δt = 10 m/s × 0.5 s = 5 m
```

这是帮助理解的例子，没有考虑转弯和加速度。如果还直接按“当前目标位置”融合旧观测，就会产生明显偏移。

V2U4Real 的 Sync 设定忽略通信延迟；Async 通过使用更早时间戳的数据，模拟 `(0, 1000] ms` 的延迟。它是在真实采集数据上构造的异步评估，和完整实车网络测试仍有距离。具体见[协同任务的评估设定](https://arxiv.org/html/2603.25275v1#S4.SS2)。

这也解释了表里 Early Fusion 为什么掉得明显。处理异步需要时间戳、运动补偿、过时消息筛选，可能还要结合不确定性。修正坐标系只能处理空间的一部分问题，目标在等待过程中已经移动了。

## Detection 之后，还要持续跟住同一个目标

Detection 关注这一帧有哪些目标。Tracking 要把前后帧的目标关联起来，维持身份，并估计运动状态。

```text
检测 → 运动预测 → 数据关联 → 状态更新 → 轨迹

t₁：ID17，x = 10 m
t₂：ID17，x = 11 m
t₃：ID17，x = 12 m
```

论文采用 tracking-by-detection，用 AB3DMOT 作为跟踪基线。它结合三维 Kalman Filter 的运动预测和 Hungarian 算法的数据关联。见[论文的跟踪任务](https://arxiv.org/html/2603.25275v1#S4.SS3)。

我把几个指标记在这里，避免只看名字猜意思：

| 指标 | 我现在的理解 |
| --- | --- |
| MOTA（Multiple Object Tracking Accuracy） | 综合惩罚漏检 FN、误检 FP、身份切换 IDSW；越高越好 |
| MOTP（Multiple Object Tracking Precision） | 看已经匹配成功的目标，定位或框的匹配质量怎样；数值方向要看具体定义 |
| AMOTA / AMOTP | 在多个召回率工作点上平均对应指标，避免只依赖一个置信度阈值 |
| sAMOTA | 对 MOTA 做与召回率有关的缩放，再综合多个工作点；阅读时要核对实现 |
| MT / Mostly Tracked | 被成功跟踪的生命周期比例超过 80% 的轨迹占比，越高越好 |
| ML / Mostly Lost | 被成功跟踪的生命周期比例不足 20% 的轨迹占比，越低越好 |

MOTA 的常见写法是：

```text
MOTA = 1 − Σₜ(FNₜ + FPₜ + IDSWₜ) / Σₜ GTₜ
```

错误很多时，它可以为负。MOTP 也不能一律理解为“误差越小越好”：有的实现平均距离误差，有的平均重叠质量。V2U4Real 表 5 将 MOTP、AMOTP 标为越高越好，读它时要跟着该评估口径走。指标实现可以参考[AB3DMOT 官方仓库](https://github.com/xinshuoweng/AB3DMOT)。

无人机可能让遮挡期间的观测更连续，给关联模块更多依据：

```text
地面观测：ID7 → 被遮挡 → 重新出现，可能变成 ID12
协同观测：ID7 → 空中补充观测 → ID7
```

但保持 ID 还取决于时间对齐、预测和关联是否正确，不能只靠多一份检测。这和 RM 自瞄、雷达里需要稳定位置、速度和轨迹的需求是连着的。

## 坐标对齐了，cross-view discrepancy 仍然存在

Pose error 是几何位置或姿态估计不准。Cross-view discrepancy 是跨视角差异：同一辆车，地面 LiDAR 更容易采到侧面，上方 LiDAR 更容易采到车顶。可见表面、点密度和特征分布都可能不同。

即使坐标变换完全正确，两边的特征也不会自动一致。模型还需要学会利用这些有差异的观测，而不是强行要求它们长得一样。

我现在会分开排查这几个问题：位置错开，检查标定和定位；时间错开，检查时间戳和延迟；位置、时间都对了但融合效果差，再看视角差异、特征编码和融合方式。它们在真实系统里也可能同时发生。

## Limitations 留下了哪些问题

论文补充材料的[Limitations and Future Work](https://arxiv.org/html/2603.25275v1#A6)明确提到：主要协同实验以 LiDAR 为主，多模态和多视角策略仍待探索；Agent 的规模和异构性有限；受空域与安全管理约束，采集区域覆盖有限。作者还计划扩展夜间、恶劣天气、越野、不同飞行高度和更大运行范围。

在这些限制之外，我自己还想继续追几件事：

- 多车、多无人机动态加入或离开时，谁和谁通信？
- 带宽有限、消息延迟或丢失时，哪些信息值得继续用？
- 定位和检测都有不确定性，融合时怎样分配可信度？
- 无人机飞到哪里能补到最多信息，又是否值得耗掉这部分电量？

其中位姿误差和异步通信已经有基线与实验研究，不能写成论文完全没碰过。主动飞行、续航调度等问题，则超出了本文主要的感知 benchmark。

## 我的延伸想法：双无人机轮换，车顶回充

读到无人机的机动性，我想到的第一个现实问题是续航。于是又问：能不能让汽车给无人机充电？如果有两架，一架飞，一架在车顶充电，再轮流接班呢？

这个设想是我从论文往外想的，论文没有提出或验证这套方案。这里的车顶充电指无人机降落后，使用接触式或近场无线充电平台；持续悬空、远距离供电还要解决另一套问题。

```text
UAV A：执行感知任务 ─────────→ 返回车顶充电
UAV B：车顶充电 → 起飞并交接 → 执行感知任务
                        ↑
                 尽量保留短暂重叠观测
```

两架也不一定能持续轮换。先假设两架无人机相同，每轮都要补回本轮消耗的电量，做一个理想化的时间检查：如果一架的可用执勤时间是 `T_on-duty`，另一架恢复可用所需的充电、准备时间分别是 `T_charge`、`T_service`，想轮换时至少要关注：

```text
T_charge + T_service ≤ T_on-duty
```

它只是粗略必要条件，飞行、返航、交接和安全余量还要单独计入。充电慢于消耗时，两机仍然会逐渐没有可用电量。充电效率、平台功率、车辆供电和散热也需要测量。

接着还有移动平台降落、接班时的目标 ID 和状态交接、掉线后的降级，以及设备成本、天气和运行区域限制。多两架无人机并不会自动完成量产落地。

我更想先把它变成一个可以验证的小问题：在遮挡严重的路口按需起飞，比较额外感知收益、能耗和通信开销，再决定什么时候换机。可以暂时用下面的目标函数表达自己的想法：

```text
max J = G_perception − λE · E − λC · C − λR · R
```

`G_perception` 是新增覆盖、检测或跟踪收益，`E` 是能耗，`C` 是通信成本，`R` 是交接风险。量纲和权重还没设计好，这不是论文公式，也不是已经可运行的算法。

到这一步，问题就涉及 active perception、energy-aware scheduling 和 multi-UAV coordination。Agent 要决定去哪里看、什么时候工作、什么时候回充，这也接上了我原先感兴趣的多智能体协作。

## 这次我带走了什么

回忆这篇论文时，我能先说出遮挡、坐标系不同、远距离点云稀疏和延迟。但 trade-off、pose error、cross-view discrepancy 这几个词，当时还讲不清。这篇笔记也是给以后复习留下一个入口。

现在我能把输入到任务的链条写出来：

```text
LiDAR 点云 → 特征编码 / BEV → 选择共享内容
                            ↓
                     通信与时空对齐
                            ↓
                     融合 → 检测 → 跟踪
```

这里每个箭头都有条件。数据能收到，还要知道它来自哪个坐标系、哪个时刻，带着多少误差。

我也重新理解了 multi-agent：车和无人机这样的实体机器人，就可以是合作感知、通信和决策的 Agent。再往后，感知可以给空间理解和世界模型提供观测，规划再决定行动；这些能力要逐层建立，读完这篇论文还只是在感知这一层入门。

对我接下来的 RM 学习，更具体的目标是把标定、坐标变换、跟踪或数据关联中的一个模块看懂：知道输入输出，能分析一次错位或丢 ID 的原因，再试着改它。之后回看 V2U4Real 的结果表，应该也会比现在多一些判断依据。
